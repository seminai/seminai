# Seminai 1.0.1 — desktop release guide

The public repository has v1.0.0 as its latest stable release. The published installer
candidate is [1.0.1-rc.2](https://github.com/seminai/seminai/releases/tag/v1.0.1-rc.2).
Its supplemental macOS Intel and Apple Silicon assets ending in `-signed` are Developer
ID signed, notarized and stapled, with Gatekeeper checks passed. Windows signing still
requires Azure authentication and authorization. Clean-machine and external-assistant
acceptance below remains necessary before the stable release.

## Runtime

Electron isolates the React renderer (sandbox, context isolation, no Node integration).
A bundled Node 22 process owns PostgreSQL 16, Prisma migrations, API, MCP and shutdown.
Services bind to loopback until the administrator enables LAN access. The database
always stays on loopback. Closing the window keeps the tray service running.

Application data is separate from the executable, under Electron's per-user data
folder in `data/`. `SEMINAI_DESKTOP_DATA_DIR` overrides it for isolated acceptance tests.
Before new migrations, the supervisor creates a stopped-database snapshot. Never
remove the data directory when updating an installer.

Desktop uses pg-boss and a PostgreSQL TTL store; the server profile keeps BullMQ/Redis.
Jobs keep progress, logs and results; retries and heartbeat leases are persistent.
Active work cannot be canceled by deleting queue metadata. A crashed worker's lease
must expire before retry; processors must retain their own domain idempotency checks.

## Manual use and optional AI

Setup creates the local administrator without contacting a model provider. Start from
Quaderno, add a company and use the manual forms for fields, production units, products
and warehouses. The journal provides activity, stock-in and stock-out commands.
Dates of operations and dates of insertion are separate.

A proposed transaction has no stock effect. The app checks permissions, units and
balances on review. Changed balances require a new review. Negative balances require
an explicit reason. Activity and its stock movements commit together. Audit rows retain
author, reviewer, input, revision and result.

Settings → Integrations → AI configures an optional provider and independent capabilities.
Secrets are encrypted. Changing a provider clears its predecessor's credential and
endpoint. The desktop restarts its API after changes; server installations must restart
their API/workers so cached services use the new configuration. Disabled or stale clients
cannot invoke a model. Provider failures do not select another paid provider.

## MCP

Claude Desktop installs `seminai-mcp-1.0.1.mcpb`. On first use, the connector opens a
Seminai authorization page. Sign in and select the company. The stored opaque grant
can read/propose only; it cannot authenticate to the ordinary app APIs. Revoke grants
in Settings → Integrations → Claude, ChatGPT and MCP.

All registered tools are scoped internal farm tools. Legacy direct-write and QDC tools
are no longer exposed. Image Line remains a separate optional in-app integration.
Streamable HTTP uses `/mcp`; external HTTPS deployments must set `PUBLIC_BASE_URL`,
`SEMINAI_API_BASE_URL`, `MCP_OAUTH_SIGNING_KEY`, `MCP_DATA_DIR` and `MCP_HOST` explicitly.
OAuth grants persist encrypted on disk; run one connector process per data directory.
Browser consent chooses a company; the access token carries only its limited grant.

ChatGPT's guided desktop configuration starts the bundled official Secure MCP Tunnel
client. A user supplies a tunnel ID and runtime key with **Tunnels Read + Use**; creating
the tunnel requires **Read + Manage**. The intended ChatGPT workspace must be associated
with the tunnel in OpenAI. The UI reports readiness and provides the official diagnostics
link. This path requires outbound HTTPS and the app must remain running. End-to-end
ChatGPT verification needs an authorized account and is a separate release gate.

## Backup and Docker migration

`Crea backup` creates a private `.zip` including PostgreSQL, attachments and recovery
keys. Restore requires the same OS, architecture and PostgreSQL major. A pre-restore
snapshot and a recoverable old directory are retained.

`Esporta per un altro sistema` creates a `.seminai` portable archive of committed
business tables, local attachments and recovery keys. Temporary cache and queue leases
are not transferred. Import builds a new database, deploys current migrations, checks
foreign keys, then switches databases. Existing data is backed up first.

For the old Docker deployment, stop the API/workers while leaving PostgreSQL running.
With this checkout and its dependencies available in the old deployment environment:

```sh
node scripts/migration/export-desktop.cjs /backup/seminai.seminai
```

Provide that environment's `DATABASE_URL`, `DATA_DIR`, and, if configured externally,
`JWT_SECRET` and `ENCRYPTION_SECRET`. Do not paste secrets into shell arguments. Copy the
archive privately, then use `Importa dati Docker / altro sistema` in the desktop app.
For S3 attachments, stage them into local `DATA_DIR/storage` before export. Keep the old
installation until counts, files and exports have been checked on the imported copy.

## Build and verify

```sh
npm ci
npm run codegen
npm run build --workspace @seminai/backend
npm run build --workspace @seminai/frontend
npm run build --workspace @seminai/mcp-connector
npm run test:desktop --workspace @seminai/backend
npm run package:mcpb --workspace @seminai/mcp-connector
npm run fetch:tunnel --workspace @seminai/desktop
npm run package --workspace @seminai/desktop
node scripts/release/desktop-assets.mjs
```

Build on the destination architecture. `desktop-installers` builds Windows x64,
macOS x64/arm64 and Linux x64/arm64 on native hosted runners. Runtime tests do not require
Docker, Redis, Ollama, API keys or system PostgreSQL. The tunnel download is pinned and
SHA-256 verified at build time; no dependency download occurs on first app launch.

## RC publication

CI and the native runtime/packaging matrix must pass before publishing a prerelease.
The initial RC assets are unsigned; subsequently signed assets have distinct names,
checksums and verification receipts. The RC is intended for the clean-machine and
external-client acceptance below. A built installer is not evidence that every supported
OS/device has passed those manual checks.

The RC tag publishes the artifacts from a successful native PR run on the exact same
commit. It also requires the full CI to have passed on that commit. Checksums are
verified before upload and against GitHub's asset digests before the draft is published.
Published releases are never overwritten by a rerun.

## Gates before the stable release

- Unify legacy stock-editing flows with the new journal's review and audit. Confirmed
  journal movements are already protected from mutation through the old stock endpoints.
- CI build, lint, unit tests, privacy scan and desktop runtime checks green.
- Clean Windows 11, macOS 13+, Ubuntu 22.04 and 24.04 installer acceptance recorded.
- Manual offline activity/stock cycle; restart, negative stock and exports verified.
- LAN mobile login/forms and backup/restore verified on a second device.
- Claude and ChatGPT proposal → in-app confirmation → one persisted movement.
- OAuth revocation, stale proposal, retry, cross-company isolation and recovery checked.
- RC assets include installers, MCPB, SHA-256 checksums, SBOM and third-party notices.
- Stable requires Windows Authenticode, macOS Developer ID signing and notarization.
  Do not label an unsigned RC as a signed stable release. Credentials belong in protected
  CI secrets, never in source. Do not create a stable tag before this evidence exists.

The update action opens GitHub Releases. Installing the next binary retains application
data and runs migrations only after its preventive backup.

The stable tag workflow accepts Azure Artifact Signing or `WINDOWS_CSC_LINK` / `WINDOWS_CSC_KEY_PASSWORD`,
`MAC_CSC_LINK` / `MAC_CSC_KEY_PASSWORD`, and `APPLE_ID`,
`APPLE_APP_SPECIFIC_PASSWORD`, `APPLE_TEAM_ID` in GitHub Actions secrets.
Signing secrets are only injected for the stable tag or an explicit signed-candidate dispatch, never in PR jobs. The tag
must also match the desktop package version. Electron Builder performs Authenticode
and Developer ID signing and its notarization integration. Validate the resulting
signatures and clean-machine installation before making the stable release public.

See [signing configuration](../desktop-signing.md) for reusing an existing Apple
identity or Azure profile. The [Docker web edition](../install.md) is a separate
installation choice for users who prefer a browser and manage their own server.
